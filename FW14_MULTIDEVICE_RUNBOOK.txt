PS4 FW14 DIRECT GOLDHEN LAB RUNBOOK
===================================

SCOPE
-----
This route is for an owned or explicitly authorized PlayStation 4 running firmware 14.00. It is a public static, click-to-run hardware validation route. It can crash or corrupt console state. Never use it on an unauthorized console.

LIVE ROUTE
----------

  https://unrealisedd.github.io/ps4-fw14-multidevice-lab/

The route is self-contained. GitHub Pages serves the reviewed exploit closure and the authorized GoldHEN image. There is no OTP, local gateway, source-IP binding, intent token, telemetry endpoint, public tunnel, or server-side evidence store.

PRE-FLIGHT
----------
1. Confirm the console is owned by you or explicitly authorized for this test.
2. Confirm firmware 14.00 in system settings.
3. Fully power off the console. Do not use Rest Mode.
4. Wait for complete shutdown, then cold boot.
5. Plan one attempt only. A refresh, back navigation, second tab, or second click is not a valid retry.

ONE ATTEMPT
-----------
1. Open the live route in the PS4 browser.
2. The page must identify firmware 14.00. Any other browser identity is refused.
3. Read the kernel-write and crash warning.
4. Check the explicit one-attempt acknowledgement.
5. Click "Dispatch pinned GoldHEN once" exactly once.
6. Do not refresh, go back, close/reopen the page, or open a second tab.
7. Wait for the terminal status.
8. Record the exact status text and whether GoldHEN became visibly ready.
9. Fully cold reboot after every outcome.

RESULT INTERPRETATION
---------------------
"GoldHEN launch dispatched" means the reviewed stage validated the HEN image, mapped it, and dispatched its entry through pthread_create after the patch/cleanup sequence. It does not prove that GoldHEN reached visible runtime readiness. Record visible readiness separately.

A failure or crash is still a consumed boot. Do not use browser refresh as a retry. Cold reboot first.

STATIC SAFETY PROPERTIES
------------------------
- No exploit or payload execution occurs on page load.
- Exact firmware identity, exact project-root route, empty query, and empty fragment are required.
- The checkbox and deliberate click create a one-shot session latch.
- The client creates a per-click cryptographic run ID and challenge locally.
- HEN is fetched only from the same Pages origin.
- The stage independently verifies HEN size, SHA-256, head bytes, mapping offset, and entry offset.
- The release workflow verifies every public file and the complete JavaScript dependency graph before deployment.

STATIC LIMITATIONS
------------------
GitHub Pages cannot enforce console source IP, mint a server-held intent, atomically consume a boot claim, maintain a durable reboot tombstone, or preserve server-side state/events/result evidence. Session storage is not a substitute for a cold reboot. Anyone who can reach the public site can download its static files, including hen.bin.

LOCAL RELEASE VERIFICATION
--------------------------
From a checkout or extracted release:

  python -B verify_release_manifest.py --root .
  python -B -W error::ResourceWarning -m unittest test_verify_release_manifest
  node --test test_github_pages_direct.mjs test_hx1400_jit_dualmap_lease.mjs test_hx1400_goldhen_dualmap_owner.mjs test_hx1400_goldhen_dualmap_stage.mjs

The first command must report MANIFEST PASS.

RETEST
------
Retest only after a real full shutdown and cold boot. Record:
- release version and commit;
- exact terminal browser status;
- whether the browser or console crashed;
- whether GoldHEN was visibly ready;
- confirmation that no same-boot refresh or retry occurred.
